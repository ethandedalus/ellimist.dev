## 1. Introduction

The default configuration produced by most Cloud SQL provisioning examples has three properties that are unsuitable for production use: the instance is assigned a public IPv4 address governed by an authorized-networks allowlist; the administrative password is generated by a random_password resource and therefore stored in cleartext in Terraform state; and applications authenticate with a static password supplied through environment configuration.

This article describes a Terraform configuration that addresses each property. The instance is provisioned without a public address and is reachable only over Private Service Access. The administrative password is generated as an ephemeral value and written through write-only attributes, so it is never persisted to state or to plan files. Applications authenticate through the Cloud SQL Auth Proxy using IAM database authentication, so no database password exists in application configuration.

The configuration is organized as reusable Terraform modules under modules/ composed by per-environment root configurations under envs/. The values cited throughout are drawn from the development environment, which is deliberately provisioned at reduced cost and durability (db-f1-micro, zonal availability, backups disabled). The module, not the development environment, is the production artifact; durability settings are parameterized

## 2. Network prerequisites

A Cloud SQL instance with a private address requires a VPC network, a subnet, and a Private Service Access connection. These must exist before the instance is created.

The network disables automatic subnet creation:

```hcl

  name                    = "${var.project_id}-vpc-${var.environment}"
  auto_create_subnetworks = false
  routing_mode            = var.routing_mode
}
```

Subnets are declared explicitly with private_ip_google_access enabled by defaulermits instances without external addresses to reach Google API endpoints,including Artifact Registry, Secret Manager, and the Cloud SQL Admin API. In this configuration, Private Google Access is sufficient for all workloads and no Cloud NAT gateway is
provisioned; the corresponding module code exists but is commented out.

## 2.1. Private Service Access

A Cloud SQL instance with a private address does not reside in the consumer VPCoogle-managed tenant project and connected to the consumer network by VPCnetwork peering. The consumer must reserve an internal address range in advance and allocate it to the service networking API. The instance subsequently receives an address drawn from
that reserved range.

Three resources are required. First, a global internal address with VPC_PEERING

```hcl
resource "google_compute_global_address" "psa" {
  purpose       = "VPC_PEERING"
  address_type  = "INTERNAL"
  address       = "10.0.64.0"
  prefix_length = 22
  network       = google_compute_network.main.id
}
```

Second, a service networking connection consuming the reserved range:

```hcl
resource "google_service_networking_connection" "psa" {
  network                 = google_compute_network.main.id
  service                 = "servicenetworking.googleapis.com"
  reserved_peering_ranges = [for r in google_compute_global_address.psa : r.name]
  deletion_policy         = "ABANDON"
}
```

Third, a peering routes configuration, which in this configuration exports and imports no custom routes.

Two properties of this arrangement affect operations. The reserved range is shared by all Private Service Access consumers in the network and cannot be resized without disruption, so it
must be sized at allocation time. The deletion_policy = "ABANDON" setting is reetworking connection cannot be deleted while dependent instances exist; without it, terraform destroy fails. The consequence is that the peering persists after the Terraform-managed resources are destroyed and must be removed separately.

The named range is referenced by the instance through the allocated_ip_range argument, which binds the instance to this reservation.

## 4. Eliminating credentials from Terraform state

### 4.1 The persistence problem

The conventional pattern generates a password with a random_password resource ance's password argument. Both the generated value and the assigned value arerecorded in Terraform state. State is not an encrypted secret store: the value is present in the state file, in the remote state backend, in any saved plan file, in continuous
integration artifacts that capture plan output, and in the output of terraform s with access to the credential is therefore the set of principals with readaccess to the state backend.

### 4.2 Ephemeral values and write-only attributes

Terraform ephemeral resources produce values that exist only for the duration of a single operation and are not written to state or to plan files. Write-only attributes, denoted by a
_wo suffix, accept such values and transmit them to the provider API without re

The configuration in modules/cloudsql/secrets.tf applies both:

```hcl
ephemeral "random_password" "postgres" {
  length  = 24
  special = false
}

resource "google_secret_manager_secret_version" "postgres_password" {
  secret                 = google_secret_manager_secret.postgres_password.id
  secret_data_wo         = ephemeral.random_password.postgres.result
  secret_data_wo_version = var.postgres_password_version
}
```

The same ephemeral value is supplied to the instance:

```hcl
root_password_wo         = ephemeral.random_password.postgres.result
root_password_wo_version = var.postgres_password_version
```

Because the value is absent from state, Terraform cannot compute a difference aach write-only attribute is therefore paired with a version attribute, and achange to that integer is the sole trigger for an update. Incrementing postgres_password_version causes the ephemeral resource to produce a new value and both consumers to receive it in
the same apply, since both version attributes reference the same variable. Creded as a change to one integer in the environment configuration.

The generated password is stored in Secret Manager. Access is granted narrowly ger_secret_iam_member, which assigns `roles/secretmanager.secretAccessor` to theTerraform service account.

These features require recent versions of both Terraform and the provider. Write-only arguments were introduced in Terraform 1.11; the configuration pins `required_version = "~> 1.14.0"`
and the Google provider at `~> 7.14.0.`

## 5. Eliminating credentials from application configuration

IAM database authentication permits principals to authenticate to a Cloud SQL via OAuth 2.0 access tokens in place of passwords. Configuring it requires changes at three layers.

### 5.1 Instance configuration

The feature is enabled by a database flag:

```hcl
flags = {
  "cloudsql.iam_authentication" = "on"
  # ...
}
```

Database users are then declared with the IAM service account type:

```hcl
resource "google_sql_user" "iam" {
  for_each = toset(var.iam_users)
  name     = each.key
  instance = google_sql_database_instance.main.name
  type     = "CLOUD_IAM_SERVICE_ACCOUNT"
}
```

Users of this type have no password.

The user name is not the full service account email. The environment configuration removes the domain suffix:

```hcl
iam_users = [
  trimsuffix(google_service_account.accounts["app"].email, ".gserviceaccount.com"),
  trimsuffix(google_service_account.accounts["keycloak"].email, ".gserviceaccou
]
```

This truncation is required because PostgreSQL identifiers are limited to 63 characters and service account email addresses commonly exceed that limit. An incorrect name does not cause
an apply-time error; it produces an authentication failure at connection time.

### 5.2 IAM bindings

Each service account requires two project-level roles, granted in the environme

```hcl
resource "google_project_iam_member" "cloudsql_client" {
  role   = "roles/cloudsql.client"
  member = "serviceAccount:${google_service_account.accounts[each.key].email}"
}

resource "google_project_iam_member" "cloudsql_instance_user" {
  role   = "roles/cloudsql.instanceUser"
  member = "serviceAccount:${google_service_account.accounts[each.key].email}"
}
```

`roles/cloudsql.client` authorizes connection through the Auth Proxy. `roles/cloudsql.instanceUser` authorizes login as an IAM database user. Both are necessary; granting one without the other produces a connection-time failure.

### 5.3 Client configuration

The application host runs the Cloud SQL Auth Proxy as a sidecar container. Frompt:

```sh
docker run -d \
  --name cloud-sql-proxy \
  --network keycloak-net \
  gcr.io/cloud-sql-connectors/cloud-sql-proxy:${cloud_sql_proxy_version} \
  --auto-iam-authn \
  --private-ip \
  --address 0.0.0.0 \
  --port 5432 \
  ${cloud_sql_connection_name}
```

The `--auto-iam-authn` flag causes the proxy to obtain an OAuth 2.0 access token account and present it in place of a password, refreshing it as it expires. The `--private-ip` flag directs the proxy to the private address allocated in Section 2.1 rather than a public endpoint.

The application connects to the proxy over the container network:

```sh
KC_DB=postgres
KC_DB_URL=jdbc:postgresql://cloud-sql-proxy:5432/keycloak
KC_DB_USERNAME=<service-account-email-without-domain-suffix>
```

No password variable is present.

### 5.4 Operational properties

The resulting configuration has four properties relevant to operations. No database credential is stored on the application host, so host compromise does not yield a reusable
credential. No credential rotation procedure is required for application accesshort-lived by construction. Access revocation is an IAM binding change and doesnot require redeployment. Connector enforcement (Section 3) prevents any path that bypasses this mechanism.

## 7. Limitations

The configuration has the following known limitations.

The deletion_policy = "ABANDON" setting on the service networking connection causes the VPC peering to persist after terraform destroy, requiring manual removal.

The Private Service Access range cannot be resized after allocation without disrupting existing consumers, so the initial /22 allocation constrains future growth.

No Cloud NAT gateway is provisioned. Workloads requiring general outbound internet access, as opposed to access to Google API endpoints, are not supported without further configuration.

The module does not provision read replicas or cross-region disaster recovery. 

Backup restoration is not exercised automatically. The backup configuration is unverified in the absence of a periodic restore procedure.                                              
The development environment disables backups and point-in-time recovery, uses zonal availability, and uses the db-f1-micro tier. These settings are not representative of a production deployment and are selected for cost.
